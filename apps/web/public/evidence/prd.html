2. 一句话定义与产品背景

一句话： 把“找智能体做任务”拆成可确认的任务计划、合格候选选择、受控执行、独立质量检查、争议处理和有证据的资金结算。

要解决的不是“再做一个聊天框”，而是三个问题：智能体能不能接这个任务；失败后由谁负责；页面上的“成功”有没有外部事实支撑。

产品假设是：需要研究、代码等交付物的发布方，希望看到明确验收条件、可解释选择和可追踪责任；Agent 提供方希望获得合理曝光、明确报酬和不被随意扣款的规则。没有本轮可查证的用户访谈、付费客户、收入或留存数据，以上是产品假设，不是市场验证结果。

按已确认简历，这是北京阿拉丁兼职经历下的项目；仓库中的课程实践标签与持续工程增强记录说明技术材料的起源和演进，不能覆盖履历归属。两层材料同时保留，不把上游 Laya/Jev 模型或框架本身算作本人原创产品，也不由兼职归属推导真实客户或营收。（E19）

6. 正常流程与失败/取消/恢复

目标业务闭环：本地模块具备，不等于当前生产全链路验收

发布方需求与验收条件
  -> 钱包会话、任务身份与权限检查
  -> 初步风险报价，发布方确认
  -> 合格候选过滤、匹配、Queen 提出计划和分配
  -> 最终报价 + 当前图版本 + 发布方和各 Agent 确认
  -> 生成资金意图，钱包签名，精确回执读回
  -> Agent 执行 -> 格式/安全 Gate -> Judge
  -> 高风险 Red Team -> AI Final Arbiter
  -> 交付物验收 -> 结算/退款读回 -> 合格评价

不同子系统的组合完整性需要端到端证据；上述箭头不宣称 9 月 UI 发布或 10 月 shadow 增强已在生产完成整条链。

补救、取消与恢复

Judge / Red Team 要求修订 -> Repair -> 再审
  修复最多 2 次；拒绝或耗尽 -> rejected
用户不批准计划 -> rejected；批准必须对应当前 revision/fingerprint
服务重启 -> 从持久化状态恢复 -> 重新检查服务端授权和操作键
外部操作已发生但响应超时 -> 对账/人工复核，不自动重复扣款
未启动链上任务取消 -> cancelBeforeStart -> 核对退款事件与状态
争议 -> 固定平台钱包 resolveTask -> 精确 TaskResolved 读回

真实历史恢复案例：Sepolia 第 17 笔 stake 领取已上链，但浏览器等待监听停止推进；以事件、独立 RPC 回执及 nonce/状态读回恢复，没有重复发送交易。它证明该次恢复，不证明所有钱包故障都已覆盖。（E03）

8. 状态机与业务规则

工作流状态，不是钱包状态

StateGraph 源码状态为 planning、awaiting_approval、executing、reviewing、repairing、completed、rejected。repairing 出现在 schema；实际 Repair 节点返回 reviewing，不能声称每个枚举都已有独立可观察迁移。

合法主路径由图定义：Queen 规划 -> approval interrupt -> Agent -> Judge。Judge 通过后，低风险走 Final Arbiter，高风险先走 Red Team；要求修订且 repairCount < 2 才进入 Repair；其他结果拒绝。最终节点再次校验 Judge 通过，高风险还必须 Red Team 通过。（E09）

确认载荷必须绑定 graphRevision 与 taskFingerprint。每个节点先调用 authorize，因此从旧 Checkpoint 恢复不是重新获得业务权限。

幂等与不确定副作用

操作键由 scope、task、图版本、fingerprint、动作和修复次数确定。Ports 必须在外部副作用前持久化去重；Checkpoint 本身不能消灭“Provider 成功、存档失败”的崩溃窗口。

Outbox 认领、发布、标记已发布存在自己的失败窗口；源码接口不证明全局 exactly-once。消费者/下游仍须幂等，消息不是授权凭证。

报价与链上状态分别约束

风险报价分 preliminary/final；最终报价必须有 Agent 分配，分配总额等于 A；初步报价不能偷带最终分配。任务、图、预算、权限或策略变更需要新报价。

V3 合约状态包含 NONE/OPEN/IN_PROGRESS/DISPUTED/SETTLED_AGENTS/SETTLED_PUBLISHER/CANCELLED。成功交易不仅检查 receipt status，还检查合约、任务及匹配事件。交易等待超时是“结果未知”，不是“没发生”。工作流 completed 不自动等于合约 settled。（E10/E15）

13. 非功能要求

安全与隐私： Hash-based Message Authentication Code（HMAC，消息认证码）保证请求完整性；keyId 对 public/owner scope 的访问控制列表分开。HMAC 不是钱包身份或任务授权。原始 Prompt、Provider key、本地路径、私有模型权重与关联钱包事件不得进入公开台账。低熵路由/分数的裸 hash 可被枚举，公开观测仍需隐私审查，不宣传“hash 就匿名”。

性能与降级： 基线即时返回，Provider 在后台观察。源码默认每 Provider 并发 1（允许配置上限 16），pending 128（上限 1024）；sink 限时默认 500 ms；Runtime Provider deadline 是两者配置最大值加 250 ms。这是代码约束，不是实测生产 P95。超时后底层工作未结束，容量仍须被占用，避免无限积压。

成本： Laya 本地模型资产约 1.69 GB 量级，不是“整个推理依赖很轻”；持久化私有记录必须单条/run/队列有界。Jev 费用和 AWS 配额独立控制，当前无完整单任务真实费用数字。不得改变免费套餐或新建重复基础设施来打卡。

维护与恢复： 小范围源码/测试/hash/receipt 一一对应；保留最初失败与修复记录；模型缺失 fail closed；启动未 ready 不泄露数据库连接；关闭结果 distinguish closed/deferred/failed。整体 Runtime 启动/收尾仍有缺口。

可用性承诺： 未测 uptime、持续吞吐、容量上限、RPO/RTO（恢复点/恢复时间目标）或生产 SLA（Service-Level Agreement，服务等级协议），不填虚构数字。

  -> 非提交者且当前获授权的审核员人工批准 / 拒绝

  -> 模拟业务记录（已有 v1）/ 持久写入意图 + Outbox（建议）
  -> Connector 执行；精确对账后投影完成状态

无权或跨企业 -> 拒绝，不返回正文或私人历史
无可靠来源 / schema 错误 -> 拒绝分析，不进入批准
撤权 / 授权被替换 / 内容或工具变化 -> 旧提交或批准失效，重新走适用阶段

17. 项目讲述稿

本轮讲述口径与连续问答（统一复习入口）

事实用“在某版本/环境实现或验收过”；未实施方案用“我会这样设计”；学习内容用“我能解释并给出检验办法”。这三种答案可共同构成完整 PRD，不能相互冒充。以下直接给出可口述回答，仍需本人作答才能判断掌握程度；企业场景属于产品假设，不代表已核实客户需求；设计完整不代表真实产品已实现全部内容。

企业身份与逐资料授权

提问：企业成员想读文档、调用工具并批准写入，你怎样判断他能不能做？

可口述回答（约 30 秒）：我把“是谁”和“能做什么”分开。输入是 session、资料引用和操作，服务端解析当前 active member，再按组织、部门、角色、文档版本和 grant 校验；输出是允许的有界结果或拒绝原因，不让客户端提交可信 principal。钱包 Owner 不自动等于企业员工，权限管理员也不自动看正文。AM v1 用假身份验证过局部机制；真实认证只是设计目标。

机制追问：为什么不只用角色 RBAC？文档 grant、缓存和待执行消息如何配合？

回答：只有 reviewer 角色还不够，同一企业不同部门也未必能看同一份资料。我会用角色做动作准入，用文档/版本/成员/action grant 约束具体资源；这是组合授权，不是给所有复杂场景堆通配规则。纯部门 RBAC 更简单，但会扩大共享范围，只有产品确实允许部门级共享时才选。缓存必须按获准资源/版本隔离，访问和执行时检查当前授权；缓存命中不能跳过检查。待执行消息携带资源和业务身份引用，而不是永久的“允许”布尔值。管理员撤销后不能再执行旧授权待办，已完成写入仍作为历史事实保留。

换约束/失败追问：成员调到另一部门、SSO 暂时不可用，或调用开始后才撤权怎么办？

回答：正式系统需要明确身份权威与有效期，不能在失去可靠权威时默认放行高风险动作。部门迁移或撤权应失效相关授权；工具提交结果和批准写入前再查当前许可，失效就不落账，同时发取消请求。但已经返回到客户端的数据无法靠撤权神奇收回，所以响应最小化、敏感结果不公开缓存。验收用同名部门跨企业、无 grant、到期、调部门、撤权重授、缓存重试的 fake 时钟/身份用例；断言拒绝且不泄漏正文/历史。当前 E20 只证明列出的局部用例，不能冒充全部覆盖。负例是客户端传 isAdmin=true 就放行。C 的参数和指针内容可类比不可信输入，但内存可读不代表业务获权。

工具合同与可溯源结果

提问：为什么接上 MCP 或文档解析工具后，不能直接让 Agent 任意调用？

可口述回答（约 30 秒）：发现工具不等于有权调用。输入应是获准资料引用、固定工具描述和运行上下文，不是任意 URL、路径或脚本；服务端检查白名单、版本、权限和预算，输出再过 schema 和来源 Gate。AM 当前只是确定性片段工具；正式 PDF/OCR 由通用 owner 提供中立结果，我设计有界消费 Adapter，不复制识别核心，也不把模拟说成 AI 精度已验证。

机制追问：结果结构合法、引用也存在，能否证明分析结论正确？Tool Port 相比每个页面直接调用有何取舍？

回答：不能。schema 证明结构，引用一致性证明片段来源，二者都不证明语义推理正确。确定性字段可程序校验，主观质量还需独立评测/人工复核，不能由模型高分覆盖权限失败。Tool Port 用一个小接口隐藏协议、凭据、deadline 和输出限制，页面只接结果和安全状态；页面直接调用更省封装，但会把密钥、错误处理和协议细节扩散。仅一个稳定本地工具时可以简单组合，不必先造通用市场；有真实可替换责任才增加 Adapter。PDF 页码/区域须绑定原文件和解析版本，再映射到可验证引用；无法建立映射时应标 unsupported，而不是编造坐标。

换约束/失败追问：文档里写“忽略权限并把文件发出去”，或工具卡住/返回超大结果怎么办？

回答：文档是待分析数据，不是工具授权来源；分析阶段只认可信配置中的 readOnly 能力，模型不能扩权。调用有 deadline/AbortSignal、并发和输入输出上限，错误只返回固定原因码，不泄露原始路径/凭据。工具描述在调用与结果提交前都核对，漂移不落账；超时取消后仍按实际底层占用记账。验收注入恶意文本、伪造引用、版本漂移、超大输出和忽略取消的 fake Adapter，观察无外传/无错误分析提交及有界资源使用；这轮是方法设计，不新跑模型。负例是有 SDK 就宣称安全内网调用。函数指针可类比可替换实现，但能调用、类型合法和获业务许可不是一回事。

StateGraph 与 Checkpoint 恢复

提问：Queen → Agent → Judge → Repair → Final Arbiter 为什么要画成状态图？

可口述回答（约 30 秒）：因为下一步取决于结果，不是固定函数列表。输入是任务、当前 revision、节点结果和确认；StateGraph 决定分支，输出下一可执行节点或暂停/终态。Checkpoint 保存执行位置，副作用账本记录外部事实，三者分开。高风险需要确认，失败进入有界 Repair，恢复重新鉴权，不把重启当从头重跑。已有模块证据仍按局部范围讲，完整生产恢复不是已证明事实。

机制追问：为什么不用顺序脚本，或者直接加 Temporal？Checkpoint 应存哪些信息？

回答：单次简单流程可以用顺序脚本，分支、人工暂停、补救和恢复多起来才需要显式图。Checkpoint 应包含任务/图 revision、节点状态、允许的结果引用、当前待确认项、预算和执行身份引用，私有结果按权限存储；恢复加载后再查真实权限和版本。Temporal 如用于长期定时、耐久执行与 Activity 重试有价值，但不会自动解决业务幂等；没有这种责任时再加一层反而增加运维和理解成本。图可以调度建议，必须保留独立 Judge/Final Arbiter 与确定性 Gate，不能让规划模型自行跳过拒绝分支。

换约束/失败追问：节点提交外部写入后宕机，用户又取消任务，恢复时怎么做？

回答：取消先阻止新的可执行节点，并向活跃调用传取消信号；已发生副作用不能被“cancelled”状态抹掉。恢复按操作键/回执查询外部状态：已完成则记事实、未发生且仍获授权才继续、未知则对账或人工审查，不能直接重发。验收在批准前、调用中、回包后保存前分别注入崩溃，用 fake Connector 的调用计数和持久日志观察没有重复副作用；再用旧 revision、撤权和新增高风险节点证明恢复不能跳过确认。闭包是短期变量环境，不是跨进程存档；ELF 装载恢复程序映像，不恢复业务执行位置。

批准的版本与授权来源

提问：审核员点了批准以后，为什么还要在写入前检查一遍？

可口述回答（约 30 秒）：批准针对一个确定快照，不是永久开关。输入是当前文档/分析/工具版本、内容身份与双方授权来源；输出是一份可被复核的批准记录。写入前重新检查，内容改版、工具变化或 grant 被替换就不能沿用。AM v1 的局部版本/授权机制验收过；正式政策版本、批准有效期和并发事务是设计补充，不说已经上线。

机制追问：审核员看 v1，提交者并发更新 v2，怎样保证不会批准错版本？为何不能只比较内容 hash？

回答：审核命令带 expectedVersion 与 analysisRef，服务端事务/条件更新同时核对版本、内容、当前状态和授权来源，不符合就拒绝，不靠前端按钮加锁。hash 证明内容身份，但不证明谁有权批准、工具/政策是否变了，也不证明批准仍有效。只有内容 hash 的方案简单，却遮蔽权限与政策变化；我选择显式版本和来源绑定，代价是需要清楚定义哪些变化使批准 stale。若批准/写入需跨存储，还要指定一致性边界，不能说 CAS 自动锁住外部系统。

换约束/失败追问：撤权后又重新授权，内容完全相同，能否复用旧批准？

回答：不能自动复用。旧提交依赖的授权来源已经失效，新 grant 是一次新授权，必须重新提交并由独立审核员确认适用快照；这也是 v1 修正的实际漏洞之一。工具运行中变版本，结果提交时拒绝，不标成旧工具成功。取消应阻止尚未发生的写入，但保留已完成记录。验收安排并发 v1/v2、撤权重授、相同文本不同分析或工具、过期批准的用例，断言没有新 mock/真实意图；前两类与工具漂移已有 E20 局部结果，其他方法不能算已跑。负例是仅存 approved=true。闭包捕获的引用仍可变，不能替代服务端版本锁。

幂等、Outbox 与副作用对账

提问：用户多点一次、队列重投一次，为什么不会写出两份业务记录？

可口述回答（约 30 秒）：输入用作用域明确的 operationKey，并绑定同一业务资源和批准；输出返回已有记录或拒绝键绑定冲突。AM 企业 v1 只用有界 Map 做进程内模拟，不能保证跨进程。正式方案要有持久唯一约束、事务内写入意图和 Outbox，外部结果未知先查询对账；我不把“接口只回一次”说成全链 exactly-once。

机制追问：为什么不用数据库写完立刻发消息？SNS/SQS/DLQ 和补偿扫描各负责什么？

回答：数据库与消息系统是两个提交点，先写后发之间会崩溃，先发后写也可能出现无账任务。事务内把业务意图和 Outbox 一起保存，派工器扫描发送；发送成功但确认丢失会重复，所以消费端还要按业务键幂等。SNS 做扇出、SQS 做有界派工/重试，DLQ 保存超过重试策略的失败消息，补偿扫描查“账有而状态不前进”的意图；DLQ 不是业务账本，也不是无限重放授权。只一个短事务且无外部副作用时可以直接写，Outbox 不是所有按钮必加；有跨系统责任时才承担它的运维成本。

换约束/失败追问：Provider 已执行但超时，不支持幂等键，取消后能否再次发送？

回答：不能以超时或取消推断未执行。我会先查稳定业务引用/外部流水，能对账再推进；既不支持幂等也无法查询时，明确不能安全自动重试，进入人工审查，不宣称 exactly-once。取消只停止未发出的动作，已发出结果待对账；消息重放也重新鉴权。验收用模拟 Connector 记录调用次数，注入 DB 提交后崩溃、重复投递、执行后丢回包、键冲突，断言一个业务效果或明确 unknown/manual_review。负例是每次重试换 UUID。Map 类比去重表，只在当前进程成立；ELF 符号唯一性不是数据库唯一约束。

超时、取消与容量账

提问：接口超时了，为什么还说后台任务占着并发容量？

可口述回答（约 30 秒）：超时是等待截止，不是实际终止。输入包括 deadline、AbortSignal 和容量上下文，输出区分及时成功、失败、取消请求和结果未知。适配器忽略 signal 时还在跑，实际 settle/退出前继续占槽位，阻止重试堆积。v1 有这一局部容量机制；生产各 Provider 和子进程的完整回收仍按各自证据讲。

机制追问：为什么 Promise.race 不能直接停止调用？等待任务结束和杀进程有什么取舍？

回答：race 只选择首先 settle 的 Promise，不自动取消其余工作。AbortSignal 是通知，Adapter 要主动传给 I/O 或检查；不服从时需要隔离运行和受控终止策略。等实际结束避免误释放，但慢任务占容量；强制终止更快，却可能丢清理和副作用结果，必须指定安全边界。查询型工具可丢弃晚到结果；写入型工具仍要保存 operationKey 并对账。内存 timer、请求超时与 Provider deadline 还要统一，不让一层已超时、下一层继续无限重试。

换约束/失败追问：用户取消后立刻重新提交，而旧调用晚到成功，会出现什么？

回答：旧调用仍活跃就拒绝/排队新请求，容量与取消身份不能被新请求覆盖；晚到只用于释放/对账，不把旧运行结果写到新 revision。真实子进程需观察退出和清理，而不是看到 signal 发送就报完成。验收用可控 Promise 忽略取消，先超时再重试，观察 active 仍在、无第二次调用、晚到无提交；再让它实际 settle，验证容量恢复。当前 E20 证明超时保留容量，不冒充其余组合也跑过。C 的返回、fd 关闭、进程退出是不同事件；JS Promise 拒绝不代表系统资源停止。

Shadow、评测与成本计数

提问：Laya/Jev 的候选模型怎样进入业务，又怎样证明它比基线好？

可口述回答（约 30 秒）：当前候选先 shadow 旁路观察，业务先返回基线，不让未校准 confidence 决定权限或金额。输入是同一任务的受限特征和候选身份，输出是候选决策、拒答、概率与延迟/计数记录。token 局部通过不证明质量更好或完整成本更低。设计上要用冻结标签集、隐私安全记录和安全发布 Gate 才讨论灰度接管，不报没有测过的提升百分比。

机制追问：为什么不用 confidence 超过一个阈值就自动选模型？sorted probability masses 有什么问题？

回答：confidence 可能未校准，阈值只是政策参数，不是可靠性证明。概率排序后若丢了 label 映射，就不能把每类概率和真实标签对应，不能据此算可信多分类校准；私有记录应保留映射和样本身份，公共 Evidence 只放允许的摘要。直接替换基线更快，但可能把效果回归暴露给用户；shadow 更安全却增加资源成本，所以要限流、deadline、样本量与保留范围。比较时冻结去重数据与划分，区分首次尝试/重试分母，记录拒答、分歧、安全失败、延迟和 reported/unknown token，不把缺失填零。

换约束/失败追问：模型超时、输出坏 JSON、标签不足或费用未知时，还能上线吗？

回答：坏输出不进入业务决策，超时取消并返回基线，底层占用照实记；费用未知单列，标签不足不能宣布已校准。先明确候选目标和允许回归，做代表性冻结集评测与关键安全用例，达到预先约定 Gate 后才评估有限灰度；这里没有新测数字。验收以离线 fake Provider 验证 fallback/坏输出/缺失计数，再用经授权的数据评测真实效果，不拿演示集代替生产分布。负例是答对几题或 token 缺失记零就宣布更便宜。C 数组排序需保留索引映射，但这个类比不证明样本代表性。

可解释匹配与公平边界

提问：新 Agent 没有历史分数，怎样既给它机会又保证任务质量？

可口述回答（约 30 秒）：我把准入和曝光分开。输入是任务约束、Agent 能力/访问范围、信誉及候选身份；先硬过滤，再规则排序，从合格新人里分配有界探索，输出候选和原因，不把不合格模型靠洗牌选进来。公平需要曝光/选择记录和可解释规则，VRF 只可能证明随机源，不能证明候选池或身份公平。相关完整公平效果是设计与评测目标，不是已经证明的数字。

机制追问：为什么不完全按历史分选，或完全随机？什么时候才引入历史数据训练？

回答：完全按历史分会让新人永远缺样本，完全随机又可能忽略能力/风险。选择先做准入 Gate、再受限探索，按类别/能力/风险分组观察曝光与履约，不保证所有人一样机会。评价资格、去重、关联主体和真实交付证据决定历史能否用；未经清洗的历史会学到刷分、曝光偏差和任务泄漏。有足够且有代表性的合法数据，再用时间/主体隔离的评测比较规则基线和学习排序，先 shadow 不直接接管。成本是日志与审计复杂度，替代方案是继续规则排序，数据不足时更可解释。

换约束/失败追问：新人反复失败、关联钱包刷好评，或随机源不可用时怎么办？

回答：质量/安全 Gate 优先于探索，失败进入限制/退出探索与补救，不为“公平”绕过验收。关联评价应拒绝或隔离，保留原因和申诉路径，不只用地址是否不同来判独立性。随机源不可用就按事先声明策略暂停随机选择或使用明确标记的替代，不伪造 VRF 证明。验收固定候选 fixture，断言越权/不合格永不召回、重复主体不放大曝光、同输入原因可解释；公平效果需真实分组测量，不能由一次通过推断。C 随机排列只是索引重排；对象引用、钱包和现实主体不等价。

链上回执与最终仲裁

提问：界面说任务完成了，就能给 Agent 打钱或者给发布方退款吗？现在 DAO 决定吗？

可口述回答（约 30 秒）：不能把界面状态当资金事实。输入是获授权意图、具体合约/方法/业务任务，输出应分别记录钱包签名、交易提交、回执、事件和结算状态。AI Judge 只是判断材料，既有 V3 的最终权威是固定平台仲裁钱包，不是 DAO 多数票。历史 Sepolia 闭环有范围和单 EOA 限制，不能证明多钱包隔离或当前网页直接发过交易。

机制追问：链上回执为什么还要核对地址和事件？若想加 DAO，替代方案是什么？

回答：status 成功只证明那笔交易执行成功，仍须核对预期链、合约、调用与匹配业务事件，不能把无关交易当本任务结算。还需声明确认/finality 策略与重组处理，具体参数不能未经场景就报为生产配置。DAO 可作为咨询或复核，也可重新设计最终裁决，但必须明确角色、仲裁规则、延迟、冲突与合约升级/迁移，不能靠改文案把固定仲裁者变成投票。固定仲裁更简单、责任明确，但中心化；DAO 增加治理与攻击面，是否采用是产品/合约决策，不是现有既成事实。

换约束/失败追问：交易已发出但页面取消，回执未找到，或者发生重组，怎么回复用户？

回答：取消页面不能撤销已广播交易，先保留原 hash 和意图身份，显示待确认/unknown，不立即重复发或宣称退款。查询精确交易及预期事件，按已定义最终性策略对账；无法判断就停止自动推进，恢复也不盲重发。验收先用模拟 RPC 注入 pending/reverted/无关事件/重组/重复响应，断言状态不会虚假 settled；真实测试链操作需独立具体授权与回读，不是本轮文档任务。负例是 HTTP 200/截图就报钱到账。ELF 链接装载可类比阶段分账，但不是共识、权限或资金证明。

SSR、Hydration 与 Cocos 私有边界

提问：为什么用 SSR/Hydration，还把 Cocos 和 Evidence 媒体延迟加载？

可口述回答（约 30 秒）：输入是路由、公开初始状态和构建版本，服务端先给可用 HTML，客户端接管交互；输出不是只有一张截图，而是可读、可降级的页面。重媒体/Cocos 按需加载降低首屏负担，失败显示真实离线状态。Cocos 只拿脱敏快照和选桌动作，不拿执行、下载或钱包权限。已有 SSR/Cocos 证据与本轮有限页面验收分账，不冒充新的全站性能提升。

机制追问：纯 CSR 更简单，为何不选它？Hydration 不匹配时怎么办？

回答：纯 CSR 可减少服务端状态一致性责任，但弱网络/大包时首屏依赖下载执行；SSR 能先读内容，代价是构建/初始状态一致性与服务端开销。选择取决于公开路由与交互需求，不是 SSR 一定更快。服务端和客户端保持同一初始版本，记录可恢复错误；严重失败只做有界 CSR 回退，不能重复循环渲染。未知路由仍真实 404。Cocos 用小消息合同与 allowlist 字段，隔离展示和业务权威；iframe 不是天然可信主体，origin/消息类型和资源身份都要检查。

换约束/失败追问：媒体加载失败、Runtime 离线、用户切路由/取消，或 iframe 伪造执行消息怎么办？

回答：旧路由请求取消或按运行身份丢弃，不把旧结果写进新页面；媒体失败保留替代文字和重试边界，Runtime 离线明确标出，不展示成功结果。iframe 只允许合同内的选桌消息，伪造批准/执行/下载一律不能推进业务。验收固定桌面/移动、语言和网络条件，检查溢出、深链、404、水合错误、切路由陈旧结果以及恶意消息；性能比较在同条件记录 TTFB/LCP/交互与错误，不从单截图推断改善。负例是 SSR 200 就宣称所有交互成功。公开对象投影可帮助理解最小字段，但 JS 私有字段、闭包和 iframe 都不能替代服务端访问控制。

为什么不用模型直接匹配/付款？先资格过滤、确定性金额和权限；模型只能在允许空间建议；shadow 评测未完成不能晋级参谋可以提意见，不能拿财务章
新 Agent 曝光怎么公平？硬过滤后，两个历史席位+合格探索席位；seeded Fisher-Yates 可复现；高风险可禁探索；算法公开不等于统计公平证明先过资格线，再给新人轮到场的机会
信誉为何不直接平均？90 天/20 事件/30 天半衰期；五维；n/(n+10) 收缩到 30；只惩罚明确归责的争议四条好评不能冒充多年老店
保证金和平台收入怎么分？发布方 P+A+B；Agent Team A；本金分配守恒、B 单独收费；quote freeze；收益未有真实商业证据工资、押金、服务费三本账
仲裁是 DAO 吗？V3 固定平台钱包；模型终审不是合约仲裁；单 EOA 测试不证明多人隔离谁能签最终裁决，要看合约，不看页面标题
Checkpoint 能保证不重复执行吗？只能保存进度；每步再授权；操作键持久去重；Provider 成功但保存失败要对账存档不是付款回执
SNS/SQS/DLQ 为什么这样分？SNS 分发、SQS 承载/重投、DLQ 隔离失败；Outbox 记录待发送；重复消费需幂等；本地规划形状不等于云已部署邮局负责投递，信件不能给人发权限
Laya 离线证明了什么？固定资产与真实加载、禁止网络、合成输入可推理；不证明业务准确率、Jev 对比或校准发动机点着了，不代表赢过比赛
token 缺失为何不用零？0 是明确报告没用；missing 是不知道；只接受非负安全整数；失败成本需另一条证据没拿到账单，不等于免费
为什么不能用 sorted probabilities 做校准？顺序丢失 label 身份，缺 ground truth/样本分母；私有完整映射还未实现分数知道了，但不知道是谁的卷子
超时为什么不能立即释放并发槽？超时只是调用方不再等待，底层可能运行；槽位保持到 settle/waitForIdle；关闭可能 deferred不接电话，不代表机器停了
如何证明“修好了”？固定 before/final hash、实际回归 receipt、独立复审；局部/全局/部署分层；历史失败保留要说清是哪一版、哪个场景、在哪里好了
